\begin{abstract}
Conditional branches create control hazards in pipelined processors: the next instruction
address is not known until the branch is resolved, so every wrong guess forces the pipeline
to discard work. This paper presents the Phase~1 design and evaluation of a dynamic branch
prediction unit written in synthesizable Verilog. The unit contains a 16-entry Branch History
Table (BHT) of 2-bit entries indexed by the branch address, a predictor core that supports
three strategies (static always-not-taken, 1-bit last-outcome and 2-bit saturating counter),
a flush and penalty interface, and hardware performance counters. The design is verified with
directed unit testbenches, a trace-driven system testbench and a Python reference model; all
12 trace and predictor combinations match the reference model exactly. On a loop-dominated
trace the prediction accuracy rises from 10.0\% (static) to 80.0\% (1-bit) and 89.5\% (2-bit),
which lowers the estimated CPI of a 5-stage pipeline from 1.360 to 1.042, a speed-up of
1.31$\times$. An alternating trace, on which both dynamic predictors reach 0\% accuracy, shows
the limit of per-branch counters and motivates the history-based predictors planned for
Phase~2.
\end{abstract}

\section{Introduction}
Pipelining improves throughput by overlapping the execution of several instructions. In the
classic five-stage RISC pipeline (IF, ID, EX, MEM, WB) a new instruction is fetched every clock
cycle, so ideally one instruction completes per cycle (CPI~=~1)~\cite{patterson2020}.
Conditional branches break this ideal. The fetch stage must choose the next program counter
before the branch condition has been evaluated, and in a simple five-stage design the branch
is resolved only in the EX stage. If the fetch stage guessed wrong, the instructions fetched
after the branch belong to the wrong path and must be flushed. This is a \emph{control hazard},
and the number of cycles lost per wrong guess is the \emph{misprediction penalty}.

Branches are frequent: in typical integer programs roughly 15--25\% of executed instructions
are branches~\cite{hennessy2017}. Even a two-cycle penalty therefore has a large effect on CPI,
and the effect grows with deeper pipelines and wider issue. A static policy such as
``always predict not taken'' is cheap but performs badly on loops, whose backward branches are
taken on almost every iteration. \emph{Dynamic} branch prediction instead records the recent
behaviour of each branch in hardware and uses it to predict the next outcome.

The goal of our project is to design, verify and compare such a predictor in hardware. The
contributions of Phase~1 are:
\begin{itemize}
\item a modular, synthesizable Verilog branch prediction unit with a 16-entry BHT and three
selectable strategies (static, 1-bit and 2-bit) behind one interface;
\item a pipeline flush interface and performance counters that measure branches,
mispredictions and penalty cycles directly in hardware;
\item four branch traces, a Python reference model and a regression flow that checks the RTL
against the model for every trace and strategy;
\item a quantitative comparison of the three strategies in terms of prediction accuracy and
estimated CPI.
\end{itemize}

Section~II reviews the literature, Section~III describes the proposed design and the
verification method, Section~IV presents the Phase~1 results, Section~V lists the individual
contributions and Section~VI outlines the plan for Phase~2.

\section{Literature Review}
\subsection{Static and simple dynamic prediction}
Smith~\cite{smith1981} carried out one of the first systematic studies of branch prediction
strategies using instruction traces of real programs. Static strategies such as ``always
taken'', ``always not taken'' and prediction by opcode were compared with dynamic strategies
that keep per-branch history in a table indexed by low-order address bits. Smith showed that
remembering only the last outcome (a 1-bit scheme) mispredicts twice for every execution of a
loop, once at the exit and once at the next entry, and that a 2-bit saturating up/down counter
removes the second error because one unusual outcome cannot flip a strongly biased prediction.
The 2-bit counter became the standard building block of hardware predictors and is the scheme
we implement as our main design.

Lee and Smith~\cite{lee1984} extended this work by studying how prediction should be combined
with fetching the branch target. They analysed Branch Target Buffers (BTBs), which store the
target address of recently taken branches so that the fetch stage can redirect without waiting
for decode, and examined the effect of table size, organisation and replacement policy on
performance. Their results show that prediction accuracy and target availability must both be
addressed to remove the branch penalty.

\subsection{History-based and modern predictors}
Per-branch counters cannot capture patterns that depend on the sequence of recent outcomes.
Yeh and Patt~\cite{yeh1991} introduced two-level adaptive prediction, in which a first level
records the history of the last $k$ outcomes in a shift register and a second level of 2-bit
counters is indexed by that history pattern. This allows a branch with a regular pattern, such
as alternating taken and not taken, to be predicted almost perfectly. McFarling~\cite{mcfarling1993}
proposed gshare, which XORs the global history with the branch address to reduce destructive
aliasing in the counter table, and the combining (tournament) predictor, which uses a selector
table to choose, per branch, between a local and a global predictor.

More recent research has moved beyond tables of counters. Jim\'enez and Lin~\cite{jimenez2001}
replaced the counters with perceptrons, simple linear neural units whose weights are learned
from the branch history; because the hardware grows linearly with history length, much longer
histories can be used. Seznec and Michaud~\cite{seznec2006} proposed TAGE, which uses several
tagged tables indexed with geometrically increasing history lengths and selects the prediction
from the longest matching history. TAGE-based designs are still the basis of many
high-performance predictors.

\subsection{Gap addressed by this work}
The textbook treatment of control hazards~\cite{hennessy2017,patterson2020} explains these
schemes conceptually, but advanced predictors are built on top of the basic mechanisms: a
table indexed by the program counter, a state machine per entry, an update path and a flush
path to the pipeline. Our project implements these foundations as synthesizable RTL with a
common interface, verifies the state transitions cycle by cycle and measures their accuracy and
CPI impact against a static baseline. The resulting unit is designed so that a BTB and a
history-based predictor can be added in Phase~2 without changing the rest of the system.

\section{Proposed Solution}
\subsection{Architecture overview}
Phase~1 implements a standalone, trace-driven branch prediction unit. A testbench reads a
trace of (PC, outcome) pairs and presents one branch to the unit per clock cycle. The unit
predicts the branch, compares the prediction with the real outcome, counts the result and
updates its table. Fig.~\ref{fig:block} shows the top module \texttt{branch\_predictor\_top}
and its sub-modules, and Table~\ref{tab:modules} summarises them. The design is written in
synthesizable Verilog~\cite{ieee1364} with parameters for the table size
(\texttt{IDX\_BITS}~=~4) and the misprediction penalty (\texttt{PENALTY}~=~2).

\subsection{Branch History Table and indexing}
Each BHT entry holds a 2-bit state. Instructions are 4-byte aligned, so the two lowest PC bits
are always zero and are skipped; the index is $\mathit{idx} = \mathit{pc}[5{:}2]$. The read is
combinational, so the state of the current branch is available in the same cycle, and the
write happens on the rising clock edge. All entries reset to 01 (weakly not-taken). Because
only four PC bits are used, branches whose addresses differ only in higher bits share an entry
(\emph{aliasing}). In our traces the branches that run together map to different entries, for
example \texttt{0x80}$\rightarrow$0 and \texttt{0x90}$\rightarrow$4 in the nested-loop trace,
so aliasing does not affect the Phase~1 results.

\subsection{Prediction and update logic}
All three predictors read the same 2-bit entry, which lets one table serve every mode.
The static predictor always predicts not taken and leaves the entry unchanged. The 1-bit
predictor predicts with \texttt{state[1]} and stores the last outcome in both bits, so after the
first update an entry is either 00 or 11. The 2-bit predictor is the saturating counter of
Fig.~\ref{fig:fsm}: a taken branch counts up, a not-taken branch counts down, the counter
stops at 00 and 11, and the prediction is the most significant bit. Table~\ref{tab:fsm} lists
the transitions. Two consecutive wrong outcomes are needed to change the prediction from a
strong state, which is what makes the counter robust at loop exits.

\subsection{Timing, flush and performance counters}
One branch is processed per clock cycle. The BHT read, the prediction and the comparison are
combinational, so \texttt{predict\_taken} and \texttt{mispredict} are valid in the same cycle
as the branch. On the next rising edge the BHT entry is overwritten with the next state and the
counters are updated. The \texttt{flush\_ctrl} module raises \texttt{flush} on a misprediction
and adds \texttt{PENALTY}~=~2 to \texttt{penalty\_cycles}, because in a five-stage pipeline
with branch resolution in EX the two younger instructions in IF and ID are on the wrong path.
Two \texttt{perf\_counter} instances count branches and mispredictions, so accuracy is measured
by the hardware itself rather than by the testbench.

\subsection{Branch traces}
Four traces of 200 branches each were generated by a Python script (Table~\ref{tab:traces}).
Each trace line is a 36-bit hexadecimal word \{PC[31:0], 3'b000, taken\} loaded with
\texttt{\$readmemh}, and an all-ones word marks the end of the trace. The same script contains
a reference model of the three predictors and writes the expected number of mispredictions for
each trace and mode.

\subsection{Verification methodology}
Verification has three levels. (1)~A directed unit testbench applies every (state, outcome)
pair to the three predictors and checks the prediction and next state: 24 cases. (2)~A BHT
testbench checks the reset value of every entry, that a write changes only its own entry, that
nothing is written when the write enable is low, and that the read is combinational: 12 checks. (3)~A trace-driven
system testbench runs the top module on each trace in each mode and prints the branch and
misprediction counts read from the hardware counters. A regression script runs all 12
configurations and compares every result with the reference model; all of them match exactly.
Waveforms of the loop trace were inspected to confirm the state transitions at each loop exit.

\subsection{CPI model}
The impact on performance is estimated with
\begin{equation}
\mathrm{CPI} = \mathrm{CPI}_{\mathrm{base}} + f_b \times m \times P,
\label{eq:cpi}
\end{equation}
where $\mathrm{CPI}_{\mathrm{base}} = 1$ is the ideal pipeline, $f_b = 0.20$ is the fraction of
instructions that are branches, $m$ is the measured misprediction rate and $P = 2$ is the
penalty in cycles. The speed-up of a predictor is the ratio of the static CPI to its CPI.

\textbf{Loops.} The 2-bit counter gives the highest accuracy on both loop traces. On the loop
trace the static predictor is wrong on every taken branch (180 errors). The 1-bit predictor
makes two errors at every loop boundary: the not-taken exit writes 00 into the entry, so the
first iteration of the next loop is also predicted not taken. This gives 20 exits, 19
re-entries and one warm-up error, 40 in total. The 2-bit counter only moves from 11 to 10 at the
exit, which still predicts taken, so it makes one error per loop plus one warm-up error, 21 in
total. Fig.~\ref{fig:wave} shows exactly this behaviour in the simulation waveforms. The same
pattern explains the nested loop, where the inner branch exits every fourth iteration and the
2-bit counter halves the mispredictions of the 1-bit predictor (46 against 88).

\textbf{CPI.} On the loop trace the 2-bit predictor lowers the CPI from 1.360 to 1.042, a
speed-up of 1.31$\times$ over the static baseline under the model of (\ref{eq:cpi}).

\textbf{Alternating pattern.} Both dynamic predictors are wrong on every branch of the
alternating trace. The 1-bit entry always holds the previous outcome, which is the opposite of
the next one, and the 2-bit counter oscillates between 01 and 10, so its prediction also flips
after every branch. The static predictor is right half of the time and is therefore 17\%
faster. This case shows that per-branch counters cannot learn patterns, which is the problem
solved by two-level predictors~\cite{yeh1991}.

\textbf{Random branches.} On the random trace the 2-bit counter reduces mispredictions from 73
to 62 compared with the 1-bit predictor, mainly on the 90\%-taken branch, where a single
not-taken outcome no longer changes the prediction. The unbiased 50\% branch cannot be
predicted better than chance by any scheme.

\textbf{Limitations.} The CPI values are estimates from (\ref{eq:cpi}) with an assumed branch
frequency, not measurements from a full pipeline. The traces are synthetic and short, and the
unit predicts only the direction of a branch, not its target.

\section{Phase 2 Plan}
Phase~2 will extend the unit towards a complete front end and a full evaluation:
\begin{itemize}
\item add a Branch Target Buffer so that the unit also supplies the target address of a
predicted-taken branch~\cite{lee1984};
\item move the table update to the EX stage (delayed update) and integrate the unit into a
five-stage RV32I pipeline, where \texttt{flush} clears the IF/ID and ID/EX registers;
\item implement a history-based predictor such as gshare~\cite{mcfarling1993} and compare it
on the alternating and nested-loop traces;
\item synthesize the design in Vivado and report resource usage (LUTs, flip-flops) and the
maximum clock frequency;
\item evaluate the predictors on longer traces taken from real programs.
\end{itemize}
