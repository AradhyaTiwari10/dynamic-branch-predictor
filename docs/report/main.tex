\begin{abstract}
Conditional branches create control hazards in pipelined processors: the next instruction
address is not known until the branch is resolved, so every wrong guess forces the pipeline to
discard work. This paper presents the design and evaluation of a dynamic branch prediction unit
written in synthesizable Verilog. The unit supports four strategies behind one interface: static
always-not-taken, 1-bit last-outcome, 2-bit saturating counter and gshare, which XORs the branch
address with a global history register. A Branch Target Buffer (BTB) supplies the target of
predicted-taken branches. The unit was first evaluated with branch traces and then integrated
into a five-stage RV32I-subset pipeline that predicts in the fetch stage, resolves and updates in
the execute stage and flushes two instructions on a misprediction, so that CPI is measured in
cycles rather than estimated. All 80 simulated configurations match a Python reference model or
instruction-set simulator. The 2-bit counter is best on simple loops (89.5\% accuracy), while
gshare reaches 98.5\% on an alternating pattern where per-branch counters fail completely and
lowers the measured CPI of a pattern-heavy program from 1.820 to 1.040 (1.75$\times$). We also
show how aliasing in a 16-entry table hurts gshare and what a 256-entry table costs in hardware
(89 to 1149 LUTs).
\end{abstract}

\section{Introduction}
Pipelining improves throughput by overlapping the execution of several instructions. In the
classic five-stage RISC pipeline (IF, ID, EX, MEM, WB) a new instruction is fetched every clock
cycle, so ideally one instruction completes per cycle (CPI~=~1)~\cite{patterson2020}.
Conditional branches break this ideal. The fetch stage must choose the next program counter
before the branch condition has been evaluated, and in a simple five-stage design the branch is
resolved only in the EX stage. If the fetch stage guessed wrong, the instructions fetched after
the branch belong to the wrong path and must be flushed. This is a \emph{control hazard}, and the
number of cycles lost per wrong guess is the \emph{misprediction penalty}.

Branches are frequent: in typical integer programs roughly 15--25\% of executed instructions are
branches~\cite{hennessy2017}. Even a two-cycle penalty therefore has a large effect on CPI, and
the effect grows with deeper pipelines and wider issue. A static policy such as ``always predict
not taken'' is cheap but performs badly on loops, whose backward branches are taken on almost
every iteration. \emph{Dynamic} branch prediction instead records the recent behaviour of
branches in hardware and uses it to predict the next outcome.

The goal of our project is to design, verify and compare such predictors in hardware. The
contributions are:
\begin{itemize}
\item a modular, synthesizable Verilog prediction unit with four selectable strategies (static,
1-bit, 2-bit, gshare), a direct-mapped BTB, a flush interface and hardware performance counters;
\item a five-stage pipeline for a subset of RV32I that uses the unit in the fetch stage with a
delayed update in the execute stage, so the CPI of each strategy is measured;
\item a verification flow with directed unit tests, a trace reference model, an instruction-set
simulator and a regression of 80 configurations;
\item a quantitative comparison of accuracy, measured CPI, the effect of table size (aliasing)
and of the delayed update, and Yosys synthesis results for two table sizes.
\end{itemize}

Section~II reviews the literature, Section~III describes the design and the verification
method, Section~IV presents and discusses the results, Section~V lists the individual
contributions and Section~VI concludes.
The source code, testbenches and results are available at

\section{Literature Review}
\subsection{Static and simple dynamic prediction}
Smith~\cite{smith1981} carried out one of the first systematic studies of branch prediction
strategies using instruction traces of real programs. Static strategies such as ``always
taken'', ``always not taken'' and prediction by opcode were compared with dynamic strategies
that keep per-branch history in a table indexed by low-order address bits. Smith showed that
remembering only the last outcome (a 1-bit scheme) mispredicts twice for every execution of a
loop, once at the exit and once at the next entry, and that a 2-bit saturating up/down counter
removes the second error because one unusual outcome cannot flip a strongly biased prediction.
The 2-bit counter became the standard building block of hardware predictors.

Lee and Smith~\cite{lee1984} extended this work by studying how prediction should be combined
with fetching the branch target. They analysed Branch Target Buffers (BTBs), which store the
target address of recently taken branches so that the fetch stage can redirect without waiting
for decode, and examined the effect of table size, organisation and replacement policy on
performance. Their results show that prediction accuracy and target availability must both be
addressed to remove the branch penalty.

\subsection{History-based and modern predictors}
Per-branch counters cannot capture patterns that depend on the sequence of recent outcomes.
Yeh and Patt~\cite{yeh1991} introduced two-level adaptive prediction, in which a first level
records the history of the last $k$ outcomes in a shift register and a second level of 2-bit
counters is indexed by that history pattern. This allows a branch with a regular pattern, such
as alternating taken and not taken, to be predicted almost perfectly.
McFarling~\cite{mcfarling1993} proposed gshare, which XORs the global history with the branch
address to reduce destructive aliasing in the counter table, and the combining (tournament)
predictor, which uses a selector table to choose, per branch, between a local and a global
predictor.

More recent research has moved beyond tables of counters. Jim\'enez and Lin~\cite{jimenez2001}
replaced the counters with perceptrons, simple linear neural units whose weights are learned
from the branch history; because the hardware grows linearly with history length, much longer
histories can be used. Seznec and Michaud~\cite{seznec2006} proposed TAGE, which uses several
tagged tables indexed with geometrically increasing history lengths and selects the prediction
from the longest matching history. TAGE-based designs are still the basis of many
high-performance predictors.

\subsection{Gap addressed by this work}
The textbook treatment of control hazards~\cite{hennessy2017,patterson2020} explains these
schemes conceptually, but advanced predictors are built on top of the basic mechanisms: a table
indexed by the program counter, a state machine per entry, a target buffer, an update path and
a flush path to the pipeline. Our project implements these foundations as synthesizable RTL with
a common interface, verifies the state transitions cycle by cycle, and measures their effect in
a real pipeline, including effects that a pure trace study hides, such as the delayed update and
the cost of a larger table.

\section{Proposed Solution}
\subsection{Architecture overview}
The design has two levels. The \emph{trace-driven unit} \texttt{branch\_predictor\_top}
(Fig.~\ref{fig:block}) receives one branch per clock from a trace, predicts it, compares the
prediction with the real outcome, counts the result and updates its table in the same cycle;
it is used to measure prediction accuracy. The \emph{pipeline unit} \texttt{bp\_unit} contains
the same table and predictor logic plus a BTB and is placed inside a five-stage pipeline
(Fig.~\ref{fig:pipe}), where prediction and update happen at different times. Table~\ref{tab:modules}
lists the RTL modules. All modules are written in synthesizable Verilog~\cite{ieee1364} and are
parameterised by the table size (\texttt{IDX\_BITS}: $2^{\texttt{IDX\_BITS}}$ entries; default 4).

\subsection{Branch History Table and the three basic strategies}
Each BHT entry holds a 2-bit state. Instructions are 4-byte aligned, so the index skips the two
lowest PC bits: $\mathit{idx} = \mathit{pc}[n{+}1{:}2]$. All entries reset to 01 (weakly not
taken). The static predictor always predicts not taken. The 1-bit predictor predicts with
\texttt{state[1]} and stores the last outcome in both bits. The 2-bit predictor is the
saturating counter of Fig.~\ref{fig:fsm} and Table~\ref{tab:fsm}: a taken branch counts up, a
not-taken branch counts down, and two consecutive wrong outcomes are needed to change the
prediction from a strong state. One table serves all modes.

\subsection{gshare}
A global history register (GHR) of $n$ bits stores the outcomes of the last $n$ branches, newest
in bit~0. In mode 3 the BHT index becomes $\mathit{pc}[n{+}1{:}2] \oplus \mathit{GHR}$, following
McFarling~\cite{mcfarling1993}, and the entry is a normal 2-bit counter. A branch therefore uses a
different counter for each recent history, which lets it learn patterns such as T,N,T,N. The
price is that different branches with different histories can map to the same counter
(\emph{aliasing}), which depends strongly on the table size.

\subsection{Branch Target Buffer}
To fetch from the target in the cycle after a predicted-taken branch, the IF stage needs the
target before the branch is decoded. The BTB has $2^n$ direct-mapped entries holding a valid bit,
a tag (\texttt{pc[31:n+2]}) and the 32-bit target. It is read combinationally with the fetch PC and
written when a branch resolves taken. A branch is predicted taken only if the direction predictor
says taken \emph{and} the BTB hits; otherwise fetch continues at $\mathit{pc}+4$.

\subsection{Five-stage pipeline and delayed update}
\texttt{pipeline\_cpu} (Fig.~\ref{fig:pipe}) implements the RV32I instructions ADD, SUB, AND, OR,
XOR, SLT, their immediate forms, BEQ, BNE, BLT, BGE and EBREAK, which stops the simulation. Data
hazards are removed by forwarding from EX/MEM and MEM/WB and by a write-through register file;
there are no loads, so the pipeline never stalls. In IF, \texttt{bp\_unit} predicts the next PC
and the BHT index it used is carried down the pipeline. In EX, \texttt{branch\_unit} computes the
real outcome and target and the real next PC is compared with the one that was fetched. On a
mismatch the IF/ID and ID/EX registers are flushed (two cycles) and fetch is redirected. The
predictor is updated in EX: the second BHT read port reads the entry with the carried index, the
new state is written back, a taken branch is written into the BTB and the outcome is shifted into
the GHR. A branch fetched within two cycles of another branch therefore still sees the old table
state and the old history. Counters record cycles, retired instructions, branches and
mispredictions, so $\mathrm{CPI} = \text{cycles} / \text{instructions}$ is measured directly.

\subsection{Workloads}
Four synthetic traces of 200 branches each are used with the trace-driven unit: \emph{loop}
(one branch, 9 taken then 1 not taken, repeated 20 times), \emph{nested\_loop} (inner T,T,T,N
inside an outer loop), \emph{alternating} (T,N,T,N) and \emph{random} (one branch taken with
$p=0.5$, one with $p=0.9$). Four assembly programs are run on the pipeline: \emph{loop} (20 runs
of a 10-iteration loop), \emph{nested\_loop} (4 $\times$ 10 $\times$ 4 iterations),
\emph{alternating} (an if/else on $i \,\&\, 1$) and \emph{pattern} (counting multiples of 3 with a
mod-3 counter, giving two period-3 branch patterns). A small Python assembler produces the
machine code.

\subsection{Verification methodology}
(1)~Directed unit testbenches check every state transition of the three predictors (24 cases),
the BHT including the second read port (14 checks), the BTB (hits, tag mismatch, overwrite,
reset; 10 checks) and the GHR and gshare index (9 checks). (2)~The trace-driven unit is run on
4 traces $\times$ 4 modes and compared with a Python reference model. (3)~A Python
instruction-set simulator executes each program, gives the expected instruction count, branch
count and result register and extracts the dynamic branch stream; this stream is run on the
trace-driven unit for 4 modes and two table sizes and compared with the reference model.
(4)~The pipeline runs every program in 4 modes and two table sizes; instruction count, branch
count and result must match the simulator, and the testbench checks the invariant
$\text{cycles} = \text{instructions} + 4 + 2 \times \text{mispredictions}$. A single script runs
all 80 configurations; all pass. Waveforms were inspected at the loop exits
(Fig.~\ref{fig:wave}).

\subsection{CPI model and synthesis}
Phase~1 estimated performance with
\begin{equation}
\mathrm{CPI} = 1 + f_b \times m \times P,
\label{eq:cpi}
\end{equation}
where $f_b$ is the fraction of instructions that are branches, $m$ the misprediction rate and
$P = 2$ the penalty. The pipeline now measures CPI, and (\ref{eq:cpi}) is evaluated with the
measured $f_b$ of each program for comparison. The prediction units were synthesized with Yosys
for a Xilinx 7-series FPGA (\texttt{synth\_xilinx}) to obtain LUT and flip-flop counts; the
logic depth was obtained from a generic 6-input LUT mapping. Vivado, which would also give the
maximum frequency after place and route, was not available on our development machines.

\section{Results and Discussion}
\subsection{Prediction accuracy on traces}
Table~\ref{tab:acc} shows the accuracy of the trace-driven unit; every value matches the
reference model. The 2-bit counter is best on the single loop: the loop exit moves the counter
from 11 to 10, which still predicts taken, so the next loop starts correctly and there is one
error per loop instead of two for the 1-bit predictor (Fig.~\ref{fig:wave} shows such a loop exit
in the pipeline). gshare is far better on nested\_loop (91.5\%) and alternating
(98.5\%), because the history tells each branch where it is in its pattern; per-branch counters
are always wrong on the alternating branch. gshare is slightly worse on loop and random: a 4-bit
history cannot see a 10-iteration loop, so the loop is spread over several counters that each
need training, and random outcomes make the history random as well.

\subsection{Measured CPI in the pipeline}
Table~\ref{tab:cpi} gives the measured CPI of the four programs with 16-entry tables. Branches
are 25--53\% of the executed instructions, more than the 20\% assumed in Phase~1, so prediction
matters even more. Static prediction costs between 0.455 and 0.820 extra cycles per instruction.
The 2-bit counter reduces the loop program to CPI~1.057 (1.38$\times$ faster than static), and
gshare gives the best result on the three programs with patterns, reaching CPI~1.040 on
\emph{pattern}, a 1.75$\times$ speed-up. Formula~(\ref{eq:cpi}) with the measured branch
frequency predicts every measured CPI to within 0.007; the remaining difference is exactly the
four cycles needed to fill the pipeline, which confirms the penalty model used in Phase~1.

\subsection{Aliasing and the delayed update}
Table~\ref{tab:alias} compares gshare with 16 and 256 entries, for an ideal predictor that is
updated before the next branch (the program's branch stream run on the trace-driven unit) and
for the real pipeline. In the ideal model with 16 entries, the alternating \texttt{beq} and the
loop \texttt{bne} of the alternating program XOR to the same counter for one of their history
patterns and keep overwriting each other, giving 203 mispredictions out of 400. With 256 entries
and an 8-bit history they no longer collide and only 9 remain. Larger tables do not always help:
on the loop programs a longer history spreads one branch over more counters, so warm-up costs
more (29 to 38 on loop).

The pipeline updates the predictor two cycles after the prediction. For the 1-bit and 2-bit
counters this made no difference in any of our programs, because no branch is fetched again
within two cycles of its own previous instance. gshare is different: when a branch follows
another branch within two instructions, the history it is predicted with is missing the newest
outcome. In the alternating program this shift happens to separate the two colliding branches,
so the pipeline has only 6 mispredictions where the ideal model has 203; in \emph{pattern} it
slightly hurts (15 instead of 11). The delayed history is therefore not simply better or worse,
but it changes which branches alias, and an evaluation based only on traces would not show it.

\subsection{Synthesis}
Table~\ref{tab:synth} lists the Yosys results. With 16 entries the complete pipeline unit (BHT,
BTB, GHR and two predictor cores) needs only 89 LUTs, 52 flip-flops and 11 LUT-RAM blocks for the
BTB tags and targets, with a longest path of 5 LUT levels. Going to 256 entries multiplies the
cost by about 13 (1149 LUTs, 776 flip-flops) and adds two LUT levels, because each table bit is a
flip-flop with reset and the read multiplexers grow with the number of entries. The trace-driven
unit has more flip-flops at 16 entries because of its three 32-bit counters. Since the logic depth
stays at 5--7 LUT levels, the predictor should not be the critical path of a simple FPGA pipeline,
but this has to be confirmed with Vivado timing.

\subsection{Limitations}
The programs are short and synthetic and the subset has no loads, stores or jumps, so the
pipeline never stalls for data and the CPI differences come only from branches. The GHR is
updated non-speculatively, which real processors avoid by updating it at fetch and repairing it
on a flush. Synthesis gives resource counts and logic depth but no maximum frequency.

\section{Conclusion}
We designed, verified and evaluated a dynamic branch prediction unit in Verilog, first as a
trace-driven unit and then inside a five-stage pipeline where CPI is measured. The results
confirm the classic findings: static prediction is poor on loops, the 2-bit counter removes the
second misprediction of the 1-bit scheme and is the best simple predictor for loops, and
per-branch counters cannot learn patterns. gshare solves the pattern problem (98.5\% on the
alternating trace and a 1.75$\times$ speed-up on the pattern program) but is sensitive to aliasing
in small tables, and the delayed update in a real pipeline changes which branches alias, an
effect that trace-only studies miss. The measured CPI agrees with the Phase~1 formula to within
the pipeline fill time, and the whole 16-entry unit costs fewer than 100 LUTs.

Future work includes a speculative global history with repair on flush, a tournament predictor
that chooses between the 2-bit counter and gshare per branch~\cite{mcfarling1993}, longer
programs with loads and stores, and Vivado place and route to obtain the maximum frequency.
